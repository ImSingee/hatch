# Native frontend

Read this reference when the App's manifest sets `app.runtime: 'native'`,
which every App created by `hatch app create` does. Read
[Design system](design-system.md) as well before writing any screen: it holds
the rules, the screen patterns and the catalogue of every component.

A native frontend is TypeScript JSX for Hatch's native runtime (NSH). Its whole
UI comes from `@hatch/ui`, a closed component catalogue that looks like the
Hatch platform and adapts to phones, tablets, desktops and the web by itself.
The same source runs in the Web Desk and in Hatch's apps, and it follows the
viewer's theme and accent without a redeploy. Widgets stay React: see
[Web frontend and widgets](frontend-web.md#widgets).

## Files

```text
app/main.tsx         the entry: `mount(App)` from @hatch/ui
app/*.tsx            more screens and helpers, imported from the entry
app/custom/          optional escape hatch for what the catalogue cannot draw
nsh.json             generated by Hatch: never write, edit or commit it
app/tsconfig.json    generated by Hatch: never write, edit or commit it
```

The entry must be directly in `app/` (`app.entry: 'app/main.tsx'`). There is
no `index.html` and no `app.html` in the manifest; Hatch serves the page.
`hatch app create`, `clone`, `update` and `adopt` write `nsh.json` and
`app/tsconfig.json` into the checkout, and every deploy writes them again from
the platform's copy. Git ignores them and NSH's `.nsh/` caches.

## Talking to the backend and Data Tables

A native frontend holds no credentials and has no network access. It reaches
its own backend and Data Tables through the shell, which sends the request
with the user's session and scopes it to this App:

```tsx
import { createClient } from '@connectrpc/connect';
import { createAppDataClient } from '@hatch/app/native';
import { createAppTransport } from '@hatch/app/native/rpc';
import type schema from '../data/schema.ts';
import { TodoService } from '../gen/service_pb.ts';

const client = createClient(TodoService, createAppTransport());
const data = createAppDataClient<typeof schema>();
```

- `client` is the generated Connect client, as on the web. Only unary methods
  work: the deploy rejects a call of a streaming method. Keep
  `@connectrpc/connect` and `@bufbuild/protobuf` in `package.json`.
- `data` has the same API as `createDataClient` from `@hatch/app/data`
  (`query`, `get`, `insert`, `patch`, `increment`, `delete`, `transaction`,
  and `watch(query, onResult, onError)` for live results). See
  [Data storage](data-storage.md).
- There is no `fetch`, no `__RPC_BASE_URL__`, no DOM (`document`, `window`)
  and no browser storage. Forms keep their own drafts on the device (see
  Forms in the design system); keep everything else in Data Tables, KV or the
  backend.
- Import npm packages only for pure logic (dates, parsing, maths) that uses
  no DOM, network or Node API. Never import a UI package (React, icon sets,
  CSS frameworks): the UI is `@hatch/ui`.

Load data with `resource` or a `signal` and show loading, empty and error
states with the catalogue (`Skeleton`, `EmptyState`, `Toast.error`). A
component is a function that runs once; read signals where they are used:

```tsx
import { List, ListItem, Page, resource } from '@hatch/ui';

function Todos() {
  const todos = resource(() => client.listTodos({}));
  return (
    <Page title="Todos">
      <List
        items={todos()?.todos ?? []}
        getKey={(todo) => todo.id}
        loading={todos.loading()}
        empty="No todos yet"
        renderItem={(todo) => <ListItem title={todo().title} />}
      />
    </Page>
  );
}
```

Check each component's props in the design system catalogue before using
it; `nsh check` rejects a prop that does not exist.

## Addresses, deep links and titles

`@hatch/ui` keeps the App's address and title in the shell, so links, pins,
reloads and the shell's back button land on the same screen. Do not call the
bridge for this yourself.

- `AppShell` puts the selected section in the address: `/<section id>`. Give
  sections short, stable, lowercase ids (`today`, `notes`). Opening the App
  with no address shows `defaultValue` (or the first section).
- A `NavStack` with `routes` adds the pages pushed in it: `/notes/42`. Without
  `routes` the address names only the section. See Addresses and titles in
  the design system for the `routes` example.
- The title of the `Page` on screen (the selected section, the top of the
  stack) is the App's title in the shell. Give every `Page` a specific title.
- List the addresses people open directly in the manifest's `app.routes`
  (`/`, `/notes`, `/notes/$id`). They are discoverability metadata for pins
  and links; they do not register anything at run time.
- To open another App, call `openApp(slug, route)` from `@hatch/app/native`.

## Rules the deploy enforces

`hatch app deploy` checks these and names the file and line of each failure
(for example `app/main.tsx:12:7: bare colour in a class`):

1. Types, through `nsh check`, including every component prop and every
   theme token named in a class.
2. Outside `app/custom/`, no import of `nsh` or `nsh/*`: UI comes from
   `@hatch/ui`. Nowhere a namespace import (`import * as x from 'nsh/base'`)
   or `export *` of an NSH module.
3. No colour written in source, `app/custom/` included: no Tailwind palette
   classes (`bg-red-500`, `text-white/80`), no arbitrary colours
   (`bg-[#f00]`) and no colour literal given to `color`, `fill`, `stroke` or a
   `*Color` key. Colours come from the theme.
4. No call of a streaming RPC method.
5. `nsh build --release` with no unknown class.
6. A start-up check: the App opens headless with canned answers (empty RPC
   replies, empty tables) and must not throw while rendering or starting.
   Code that runs at start-up must handle empty data and failed calls.

`app/custom/` is for what the catalogue cannot express (a canvas, a game).
Files there may import `nsh` directly but still use only theme tokens in
classes (`bg-card`, `text-muted-foreground`, `rounded-(--radius-md)`). The
build log lists every custom file; use the catalogue whenever it can do the
job.

## Checks before deploying

Run these from the App root (all with `run_command`):

```bash
nsh check
tsc -p .hatch/tsconfig.native.json
nsh build --release
nsh test app/main.tsx
```

- `nsh check` type-checks the native frontend against the generated
  `app/tsconfig.json`. A type error names `app/<file>(line,col)`.
- `tsc -p .hatch/tsconfig.native.json` checks everything else (backend,
  widgets, `data/schema.ts`, `gen/`). Do not use `.hatch/tsconfig.json` in a
  native App: it would check `app/` as React code and fail.
- `nsh build --release` must print no `unknown class` warning.
- `nsh test app/main.tsx` opens the App headless and fails if it throws while
  starting. It has no shell, so RPC and Data Table calls fail there; the App
  must show an error state, not crash.

If `nsh` or `nsh.json` is missing, run `hatch app update --directory <path>
--json` (it needs a clean tree) to prepare the checkout again. The deploy runs
the same checks in any case, so when a command is unavailable, deploy and fix
what it reports.

Do not write UI tests: end-to-end and screenshot tests are not supported. Keep
unit tests to logic that is easy to get wrong, in plain `.ts` files outside
`app/`.

## Keyboard shortcuts

Hatch's shortcuts work inside a native App as inside a web App, and the
manifest's `keyboard.reserve` lets the App keep a chord for itself: see
[Web frontend and widgets](frontend-web.md#keyboard-shortcuts).
